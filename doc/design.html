4.1 项目基本需求

4.1.1 项目定位

知识库 KBase 是一个面向个人（或小团队）的知识库管理系统，旨在提供一个轻量级、本地化部署的知识管理解决方案。用户可以通过浏览器访问系统，创建多个独立的知识库（Tab），以树形目录组织知识条目，通过富文本编辑器撰写和保存内容，并借助全文搜索和 OCR 文字识别功能快速检索知识。

4.1.2 核心用户场景

  • 知识整理：收集和整理技术文档、学习笔记、项目资料等
  • 本地搜索：对大量知识内容进行全文关键词搜索，包括图片中的文字
  • 数据导出：将知识库打包备份或导出为独立 HTML 页面

4.1.3 版本说明

  • 个人版，无登录密码保护，所有功能在本地网络内可直接访问
  • 支持 Windows / Linux / macOS 三大平台
  • Python 运行环境要求 >= 3.8

4.1.4 功能清单

4.4.1.3 导出系统详细说明

导出 系统支持两种粒度的导出，每种支持 PDF 和 ZIP 两种格式：

  • Tab 级导出：在 Tab 右键菜单中选择「Export」→「PDF/ZIP」，导出整个知识库的所有内容
    • PDF：将 Tab 下所有菜单项递归收集，生成一个 PDF 文档，使用 NotoSansSC 字体（CJK 支持）
    • ZIP：直接将 Tab 的数据文件夹（data/mybase/<tab>/）打包为 ZIP
  • 菜单项级导出：在树形菜单项的右键菜单中选择「Export」→「PDF/ZIP」，导出该菜单项及其子树的全部内容
    • PDF：递归收集子树所有菜单项，合并在一个 PDF 中，按深度缩进层次
    • ZIP：生成独立的 HTML 页面（包含所有子树内容序列化为 JSON 的交互页面），复制引用的图片到 images/ 目录，打包为 ZIP

4.4.1.4 WebSocket 实时同步

同步 系统基于 flask-socketio 实现跨窗口实时同步：

  • 架构：采用 Socket.IO 协议，支持房间（Room）机制的广播通信
  • 房间结构：
    • tab:{tab_name} — 用于同步菜单结构变更、知识库重命名/删除等
    • tab:{tab_name}:notify — 用于同步生命周期事件（如加密知识库解锁/密码变更）
    • doc:{tab}:{item_id} — 针对单个文档的编辑房间，用于实时内容同步和锁定
  • 核心事件：
    • 客户端 → 服务端：join_tab, leave_tab, join_document, leave_document, content_change, lock_document, unlock_document
    • 服务端 → 客户端：content_update, menu_changed, content_saved, sync_denied, lock_acquired, lock_denied, tab_added, tab_renamed, tab_deleted, encrypted_tab_password_changed, encrypted_tab_decrypted
  • 文档锁定机制：防止多人（或多窗口）同时编辑冲突。当用户开始输入时自动申请锁定，锁定状态与 Socket 会话绑定，断开连接自动释放
  • 安全性：加密知识库禁止通过 WebSocket 同步内容。所有同步请求会验证知识库是否加密，若已加密则拒绝同步内容变更，仅允许同步解锁状态

4.4.1.5 Cython 编译与打包

构建 为了提高性能和保护源代码，系统支持 Cython 编译：

  • setup.py：使用 Cython 将 server.py 编译为二进制扩展模块（Linux/macOS 为 .so，Windows 为 .pyd）
  • main.py：一个轻量级的加载器，负责导入编译后的模块并启动服务器
  • Makefile 目标：
    • all — 默认构建
    • build — 执行 Cython 编译
    • clean — 清理编译产物和临时文件
    • package — 打包为适用于 Linux/macOS 的发布包
    • package-win — 打包为适用于 Windows 的发布包
  • 发布包内容：包含编译后的扩展模块、web/ 目录、doc/ 目录、models/ 目录、pdf_fonts/ 目录、requirements.txt、main.py 以及 README.md

4.4.2 UI 界面设计

4.4.2.1 整体布局

采用经典的三栏式布局结构（IDE 风格），从上到下依次为：

  • Tab 栏（顶部深色条）— 显示所有知识库标签，支持拖拽排序、滚动、右键菜单
  • 主内容区（剩余空间）— 左右分割：
    • 左侧侧边栏 — 树形菜单 + 工具栏（固定宽度 280px，可拖拽调整）
    • 右侧编辑区 — 富文本编辑工具栏 + 编辑区 + 状态栏
  • 搜索结果面板（底部，可折叠）— 搜索结果显示区域，带可拖拽分割条

4.4.2.2 Tab 栏界面

  • 背景色：#2c3e50（深蓝灰）
  • Tab 标签：圆角矩形，悬停高亮，激活状态为白色背景
  • 拖拽时显示蓝色边框指示放置位置
  • 溢出时左右出现 ‹ › 滚动按钮
  • 支持鼠标滚轮水平滚动

4.4.2.3 侧边栏界面

  • 顶部 ☰ Menu 下拉按钮：全部收起 / 全部展开 / 新增根菜单项
  • 树形菜单：缩进式多级嵌套，每级缩进 20px

4.4.3.2 前端架构（HTML + JS + CSS）

前端 采用 纯原生 JavaScript 单页应用（SPA） 架构，无任何前端框架依赖：

  • HTML（index.html）：单页面模板，包含所有界面元素和弹出对话框的 DOM 结构
  • CSS（style.css）：层叠样式表，约 1607 行，采用 Flexbox 布局，响应式设计
  • JavaScript（app.js）：约 3847 行，IIFE 模式封装，模块化组织：
    • API 层：api() 和 apiUpload() 统一封装 fetch 请求
    • Tab 管理：加载、切换、拖拽排序、右键菜单、增删改
    • 树形菜单：渲染、展开/折叠、节点选中、右键菜单
    • 编辑器：富文本操作（execCommand）、粘贴处理（图片自动上传）、链接点击
    • 搜索：参数构建、结果渲染、导航跳转
    • 其他：备份进度轮询、索引状态轮询、字体配置保存、列宽拖拽调整

4.4.3.3 后端架构（Python / Flask）

后端 采用 Flask 轻量级 Web 框架：

  • 路由层：@app.route 装饰器定义 RESTful API 端点，返回 JSON 或 HTML 模板
  • 业务逻辑层：纯函数实现（无类封装），包括菜单操作、索引构建、OCR 调度等
  • 数据访问层：
    • 文件系统：HTML 内容文件（content/*.html）、图片文件（images/）、菜单 JSON 文件（menu.json）
    • SQLite 数据库：common.db（配置）/ index_db/*.db（搜索索引）
  • 设计模式：函数式编程风格 + 模块化组织，少量辅助类（OCRProcessPool）

4.4.3.4 进程线程模型

🔹 Flask 主线程

单进程 + threaded=True 模式，每个 HTTP 请求由线程池处理。负责所有 REST API 的同步处理和响应返回。同时运行 SocketIO 事件循环，处理实时同步请求。

🔸 后台线程池

通过 _run_in_background() 创建的 daemon 线程，用于索引构建、索引更新、备份打包等耗时操作，不阻塞主线程。

🔹 OCR 进程池

通过 multiprocessing.Process 创建，每个进程持有 1 个独立的 PaddleOCR 实例，避免 GIL 限制和 fork 安全问题。

🔸 ThreadPoolExecutor

菜单项索引时使用 concurrent.futures.ThreadPoolExecutor 并行处理（--workers-menu 控制并行度），OCR 调用共享进程池。

4.4.3.5 进程间通信机制

通信对机制说明
Flask 主线程 → OCR 进程池 multiprocessing.Queue 主线程通过 task_queue.put((task_id, image_path)) 提交 OCR 任务
OCR 进程池 → Flask 主线程 multiprocessing.Queue OCR 进程通过 result_queue.put((task_id, text)) 返回识别结果
队列收集 → 结果分发 threading.Condition 后台 collector 线程持续 drain result_queue，通过 Condition 通知等待的调用方
后台索引线程 → 主线程 threading.Lock + int_counter 索引状态通过加锁的全局计数器 _indexing_counter 暴露给 /api/indexing-status 查询
备份线程 → 主线程 threading.Lock + dict 备份进度存储在 _backup_tasks 字典中，通过锁保护，前端通过轮询获取

4.4.3.6 异常处理策略

场景处理方式
OCR 模型加载失败 日志记录错误，进程退出，不影响主服务器运行
OCR 单张图片识别超时 batch_timeout（默认 300s）后跳过，返回空字符串，不影响其他图片
OCR 进程挂起 主线程超时后标记跳过，不等待。shutdown 时 join 超时则 terminate()
SQLite 操作异常 try/finally 保证连接关闭；调用方捕获异常后记录日志
文件读写异常 log_error() 记录到文件和控制台，不中断主流程
Ctrl+C 中断 设置 _shutdown_requested 事件 → 工作线程自行退出 → OCR 进程池 shutdown → 进程 terminate
无效的正则表达式 返回 HTTP 400 + 错误信息，前端显示错误对话框
PaddleX/PaddleOCR C++ 日志 环境变量（GLOG_*, FLAGS_*）抑制框架层日志；suppress_stdout_stderr 上下文管理器在 FD 级别重定向输出

4.4.3.7 关键设计决策

决策选择理由
OCR 并行方式 多进程（非多线程） PaddleOCR 推理计算密集，多线程受 GIL 限制；多进程每个进程独立实例，充分利用多核 CPU
搜索索引存储 SQLite 每 Tab 独立 .db 文件 避免单文件锁竞争；WAL 模式支持读写并发；无需额外部署数据库服务
内容存储 文件系统（HTML 文件） 直接以 HTML 格式存储，无需序列化/反序列化；便于独立导出和调试查看
前端框架 原生 JS（无框架） 轻量、零依赖、快速加载；项目复杂度可控，原生 JS 即可满足需求
索引构建策略 批量插入（非逐条） 避免 SQLite 写竞争：收集所有结果后在单线程中 batch INSERT
Windows 兼容 限制 workers=1 Windows 无 os.fork()，multiprocessing 行为不同，限制为单进程避免异常
OCR 模型选择 --mobile-ocr 参数 / 平台自动检测 Windows 默认使用 Mobile 模型避免兼容性问题；Linux 使用 Server 模型获取更高精度。通过 ocr_version="PP-OCRv5" 统一指定版本，用 text_detection_model_name / text_recognition_model_name 区分 mobile/server 模型

4.4.4 关键技术设计

4.4.4.1 OCR 图片文字识别

技术 基于 PaddleOCR 开源 OCR 引擎：

  • 模型：使用 ocr_version="PP-OCRv5" 统一框架。通过 --mobile-ocr 参数选择变体：
    • Mobile 模型（--mobile-ocr true，Windows 默认）：PP-OCRv5_mobile_det（文字检测）+ PP-OCRv5_mobile_rec（文字识别）+ PP-LCNet_x1_0_doc_ori（方向分类）+ UVDoc（文档矫正）。内存占用低，适合资源受限环境
    • Server 模型（--mobile-ocr false，Linux 默认）：PP-OCRv5_server_det（文字检测）+ PP-OCRv5_server_rec（文字识别）+ PP-LCNet_x1_0_doc_ori（方向分类）+ UVDoc（文档矫正）。精度更高，内存占用更多
  • 初始化：每个 OCR 工作进程在 _ocr_worker_init() 中创建独立的 PaddleOCR 实例，设置 lang='ch'（中文），device='cpu'。启动时根据 os.environ['OCR_MOBILE'] 选择 mobile/server 模型参数
  • 调用流程：
    1. extract_text_from_html_images() 扫描 HTML 中的 <img> 标签
    2. 支持三种图片源：URL 引用（/uploads/<tab>/images/）、相对路径、Base64 内嵌图片
    3. Base64 图片解码为临时 PNG 文件
    4. 所有图片路径提交到 OCRProcessPool.predict_batch()
    5. 每个图片进入任务队列 → OCR 进程处理 → 结果队列返回
    6. 收集所有识别文本，合并为字符串返回
  • 超时机制：每张图片从开始处理计时，超过 batch_timeout（默认 300s）则跳过
  • 模型缓存：存储在 models/ocr/official_models/ 目录，使用环境变量 PADDLE_PDX_CACHE_HOME 指定

4.4.4.2 全文索引引擎

技术 基于 SQLite 内置的全文索引能力：

索引数据库表结构（每 Tab 一个 .db）：

列名类型说明
menu_item_idTEXT PK菜单项 UUID
labelTEXT NOT NULL菜单项名称
content_textTEXT DEFAULT ''去 HTML 标签后的纯文本 + OCR 识别文本
menu_pathTEXT NOT NULL完整路径（Tab名/父项/子项）

索引构建流程：

  1. 全量索引 index_tab()：
    • 遍历菜单树，展开为扁平列表
    • 并行处理每个菜单项（ThreadPoolExecutor）
    • 每个项：读取 HTML 内容 → 去标签 → OCR 图片文字提取 → 收集结果
    • 单线程 batch INSERT 到 SQLite（避免写竞争）
  2. 增量索引 update_item_in_index()：
    • 保存内容后后台线程执行
    • 单条目：DELETE + INSERT OR REPLACE
  3. 路径更新 update_item_path_in_index() / update_item_meta_in_index()：
    • 菜单项移动或重命名时仅更新路径/标签，不重做 OCR

搜索实现：

  • 普通搜索（简单模式）：SQL LIKE '%query%' 匹配 label 和 content_text，限制返回 50 条
  • 普通搜索（OR/AND/排除模式）：全表扫描，Python 逐行过滤：
    • aaa | bbb | ccc — OR 模式，匹配任一关键词（| 分隔）
    • aaa bbb ccc 或 aaa && bbb && ccc — AND 模式，所有关键词必须同时存在（空格或 && 分隔）
    • aaa ^ bbb — 排除模式，^ 前的词必须存在，^ 后的词必须不存在
  • 正则搜索：全表扫描，Python re.compile().search() 逐行匹配，支持 | 语法
  • 片段生成：make_snippet() 在匹配位置前后截取 40 字符上下文
  • 搜索范围：当前 Tab 或全部 Tab（遍历 index_db/*.db）
